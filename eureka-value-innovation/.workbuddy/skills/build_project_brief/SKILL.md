# Build Project Brief Skill

**Skill Name**: `build_project_brief`

**Description**: 构建项目简报（Project Brief, PB），作为整个价值创新项目的基石。将客户的需求描述转化为结构化的项目框架，明确背景、挑战、目标和范围。

## 触发场景

当用户满足以下任一条件时触发：
- 提出一个价值创新项目需求（自然语言描述）
- 要求使用"Eureka系统"开始一个新项目
- 描述需要解决的问题或机遇

## 工作流程

### 步骤 1: 分析输入需求
从用户需求中提取关键信息：
- 核心问题/机遇是什么？
- 背景场景有哪些约束？
- 涉及哪些用户群体？
- 有什么时间/资源限制？

### 步骤 2: 定义核心设计挑战
基于需求，构建清晰的设计挑战陈述：
- 遵循"如何为[目标用户]设计[目标成果]，以[核心价值]"格式
- 确保挑战具体、可行动、有激励性

### 步骤 3: 识别目标用户
明确项目的核心用户群体：
- 用户画像（角色、背景、特征）
- 用户需求/期望
- 用户旅程关键触点

### 步骤 4: 确定共识目标
定义项目的共识目标和成功标准：
- 具体可衡量的目标
- 成功的标准是什么？
- 期望的成果交付物

### 步骤 5: 识别利益相关方
列出所有关键利益相关方：
- 决策者、影响者、执行者、受益者
- 各方的关注点和需求

### 步骤 6: 设定时间窗口
定义项目时间范围和关键里程碑：
- 项目周期
- 关键阶段时间点
- 交付时间安排

## 输入数据

**Source**: 客户需求描述（自然语言）

示例：
```
"用户需要在工作回顾中做出更明确的承诺，而不是只列出要做的事情。当前的问题是Alice每周回顾中只说打算做什么，但没有说必须做到什么，导致目标不清晰，无法追踪进展。"
```

## 关键原则

1. **清晰性**: 所有陈述必须简洁明确，避免歧义
2. **可行动性**: 目标和挑战必须可转化为具体行动
3. **用户中心**: 始终以目标用户为中心，理解其真实需求
4. **共识驱动**: 确保所有利益相关方对目标有共同理解
5. **时间约束**: 明确时间窗口，保持项目可控性

## 错误处理

### P1 错误（必须处理）
- 输入需求为空或过于模糊 → 返回错误，要求用户补充信息
- 无法识别目标用户 → 使用通用占位符并标记警告
- 无法定义时间框架 → 设置默认值（3个月）并标记警告

### P2 错误（可容忍）
- 利益相关方信息不完整 → 使用现有信息，标记"待确认"
- 用户旅程触点不清晰 → 使用典型场景推断

## 与其他Skill的协作

**上游**: 无（这是第一个Skill）

**下游**:
- `pov_builder`: 使用Project Brief中的target_user和background构建用户POV
- `roleplay_stakeholder`: 使用stakeholders信息进行利益相关方模拟
